# Tasquest 設計ドキュメント

> 本書は、目標管理サービス「Tasquest」の設計方針および決定事項をまとめたものである。
> 議論により確定した事項と、その根拠を記録する。

- 最終更新: 2026-09-12
- ステータス: Phase 1 着手前 / 設計確定

---

## 1. コンセプト

複数の目標を並行して管理し、AI が各目標を「フェーズ」と「クエスト」に分解することで、
目標達成をロールプレイングゲーム的な体験として継続可能にする個人用 Web サービス。

参考とした既存サービスは GOALhack（AI が目標をクエスト化する目標達成 RPG）である。
本サービスは自分専用のサービスとして構築し、AI 利用に伴う追加課金を発生させないことを制約条件とする。

---

## 2. 決定事項サマリ

| # | 論点 | 決定 | 根拠 |
|---|---|---|---|
| D-1 | 目標の管理単位 | 複数目標の並行管理。ただしアクティブ枠は 3 件に固定 | 進捗の分散による達成感の希薄化を防ぐため |
| D-2 | ゲーム要素 | 必須要素として実装する（XP / レベル / ストリーク / フェーズ） | 継続性がサービスの中核価値であるため |
| D-3 | XP・レベルの帰属 | プレイヤー（アカウント）に単一。目標側はフェーズのみ保持 | 目標ごとにレベルを持たせると全目標が低レベルに留まるため |
| D-4 | AI の責務境界 | AI は「内容」のみ決定。数値・判定はアプリ側の決定論的ロジック | プロバイダ差し替え時にもゲームバランスを不変に保つため |
| D-5 | 生成主体 | 日次は無料枠 API による自動生成、週次は Cowork による手動対話 | 追加課金を発生させずに自動化を得るため |
| D-6 | AI への送信データ | 要約情報（目標メタ・フェーズ・直近 7 日の実行パターン）に限定 | 生成精度およびトークン効率のため（副次的にプライバシー保護） |
| D-7 | 未達時の扱い | ストリークは途切れる。XP は減算しない。休息トークンで一定数を吸収 | 罰ではなく診断のトリガーとして機能させるため |
| D-8 | フェーズ設計 | フェーズ数（4）と遷移条件はアプリが固定。名称と狙いは AI が目標ごとに生成 | 決定論的な進行管理と目標ごとの個別性を両立させるため |
| D-9 | フェーズの編集 | ユーザーによる編集を許可し、編集済みフェーズは AI の上書き対象外とする | 編集内容が AI に破壊される事故を構造的に防ぐため |
| D-10 | DB への書き込み経路 | AI からの書き込みは 3 本の RPC のみに限定。生 SQL は許可しない | 想定外の破壊的操作およびスキーマ不整合を防ぐため |
| D-11 | UI の方向性 | 画面そのものをゲーム盤面として構成する。暗色背景にシアンの発光を用いたホログラム調 | 開いた時点で継続の動機が働くことを重視したため |

## 3. システム構成

```
[Next.js on Vercel]  記録UI / クエスト表示 / レベル・ストリーク
        |
        |  Supabase Auth + Row Level Security
        v
[Supabase PostgreSQL]  player / goals / goal_phases / quests / logs / retrospectives
        ^                                    |
        | 読み取り                            | 書き込みは RPC 3 本のみ
        |                                    |
[生成主体（差し替え可能）]
   - 日次: Vercel Cron -> 無料枠 LLM API（自動）
   - 週次: Claude Cowork -> Supabase MCP（手動）
```

### 3.1 技術スタック

| レイヤ | 採用技術 | 備考 |
|---|---|---|
| フロントエンド | Next.js (Vercel Hobby) | 無料枠 |
| データベース | Supabase PostgreSQL | 無料枠。7 日間無操作で一時停止する点に留意 |
| 認証 | Supabase Auth（単一ユーザー） | RLS 必須 |
| 日次生成 | Vercel Cron + 無料枠 LLM API | Hobby プランの Cron は 1 日 1 回、指定時刻の 1 時間以内に発火 |
| 週次対話 | Claude Cowork + Supabase リモート MCP | `https://mcp.supabase.com/mcp`（OAuth） |

### 3.2 前提の検証状況

| 前提 | 状況 |
|---|---|
| Cowork から Supabase への MCP 接続 | 検証済み。公式ホスト型リモート MCP サーバが提供されており、Cowork はカスタムコネクタに対応 |
| MCP 経由の書き込み | 可能。既定は書き込み可、`read_only` パラメータで読み取り専用化 |
| 無料枠 LLM API の容量 | 十分。必要量は 1 日 1〜3 リクエストに対し、無料枠は 250〜1,000 リクエスト/日 |

## 4. データモデル

```sql
-- プレイヤー（1 行のみ）
player(
  id, level, total_xp, current_streak, longest_streak, rest_tokens
)

-- 目標
goals(
  id, title, why,
  status,                  -- active | backlog | done | abandoned
  active_slot,             -- 1..3。unique index によりアクティブ枠を 3 件に制限
  share_with_external_ai,  -- default true。外部 AI への送信可否
  created_at
)

-- フェーズ（目標ごとに 4 件）
goal_phases(
  id, goal_id,
  phase_no,                -- 1..4
  name, intent,            -- AI が生成
  quests_required,         -- 遷移条件。アプリが決定
  status,                  -- locked | active | done
  edited_by_user           -- default false。true の場合 AI の書き戻し対象外
)

-- クエスト
quests(
  id, goal_id, phase_id,
  title, why,
  effort,                  -- S | M | L。AI が決定
  xp_value,                -- effort からアプリが決定
  status,                  -- open | done | missed
  due_on,
  generated_by,            -- cowork | gemini | manual
  generated_at
)

-- 記録
logs(
  id, goal_id, quest_id, body, logged_on
)

-- 振り返り
retrospectives(
  id, goal_id,
  kind,                    -- miss | weekly
  status,                  -- open | resolved
  trigger_quest_ids,
  insight,                 -- Cowork 経由で書き戻される
  resolved_at
)

-- XP 加算の監査ログ（total_xp はこの集計により導出）
xp_events(
  id, source, quest_id, amount, created_at
)

-- AI 実行履歴
ai_runs(
  id, provider, model, purpose, prompt_summary, created_at
)
```

### 4.1 設計上の要点

- **アクティブ枠の制限は DB 制約で行う。** `active_slot` に対する unique index により、アプリ層のバリデーションを迂回した書き込みでも 3 件を超えないことを保証する。
- **`total_xp` は `xp_events` の集計により導出する。** AI は `player` テーブルへの書き込み経路を持たないため、ゲームバランスを破壊し得ない。
- **`goal_phases` は Phase 1 時点から作成する。** Phase 1 ではフェーズ機能を使用しないが、後続フェーズでのマイグレーションを回避するため、スキーマは完成形で構築する。

## 5. AI の責務境界

本設計における最重要の原則は、**AI は内容のみを決定し、数値および判定はアプリケーションが決定する**ことである。

| 決定主体 | 対象 |
|---|---|
| **アプリ（決定論的）** | XP 値、レベル曲線、ストリーク計算、休息トークン消費、フェーズ数（4 固定）、フェーズ遷移条件 |
| **AI（生成）** | クエストの内容・理由・工数区分（S/M/L）、フェーズの名称・狙い、未達要因の考察 |

この分離により、生成主体を Cowork・無料枠 API・その他のいずれに差し替えても、ゲームバランスは不変となる。

### 5.1 AI に許可する書き込み経路

AI からの書き込みは以下の 3 つの RPC に限定する。生 SQL による書き込みは許可しない。

```sql
propose_quests(p_payload jsonb)
-- 受け取る: goal_id, title, why, effort
-- 受け取らない: xp_value（effort からアプリが決定）

propose_phases(p_goal_id uuid, p_phases jsonb)
-- 受け取る: name, intent
-- edited_by_user = true のフェーズは無視する

record_insight(p_retro_id uuid, p_insight text)
-- 振り返り結論の書き戻し
```

### 5.2 生成主体の役割分担

| | 日次クエスト生成 | 週次作戦会議・未達相談 |
|---|---|---|
| 実行主体 | Vercel Cron + 無料枠 LLM API | Claude Cowork（MCP 経由） |
| トリガー | 自動（毎朝） | 手動 |
| 入力データ | 目標メタ、フェーズ、直近 7 日の実行パターン、未達パターン | 記録全文を含む詳細データ |
| 用途 | 定型的なクエスト生成 | 未達要因の深掘り、フェーズ再設計 |
| コスト | 無料枠内 | Claude プラン内 |

## 6. ゲームメカニクス

### 6.1 XP とレベル

- クエスト完了時に、工数区分に応じた XP を付与する（例: S=10 / M=25 / L=60）。
- XP はいかなる場合も減算しない。
- レベルは `total_xp` に対する純粋関数として算出する。

### 6.2 ストリークと未達

```
クエスト未達
  -> 休息トークンが残存する場合、これを消費して吸収（ストリーク維持）
  -> 残存しない場合、current_streak を 0 にリセット
     （XP は減算しない。longest_streak は保持する）
  -> retrospectives に kind=miss / status=open のレコードを自動生成
  -> Cowork での対話により要因を分析し、insight を書き戻す
  -> 同一目標で 3 回連続未達が発生した場合、
     AI がクエストの工数区分引き下げ、またはフェーズの巻き戻しを提案する
```

- **休息トークン**は週 1 枚を上限として補充する。完璧主義による離脱を防ぐことを目的とする。
- **未処理の振り返りが 5 件を超えた場合、新規レコードは生成せず既存に集約する。** 未処理項目の累積による心理的負荷を抑制するための措置である。

### 6.3 フェーズ

- 全ての目標は 4 つのフェーズを持つ。
- 各フェーズの名称と狙いは AI が目標ごとに生成する（例: 発音矯正期 / 原稿作成期 / 通し練習期 / 本番調整期）。
- フェーズ遷移は「当該フェーズのクエストを規定数完了する」という決定論的条件により判定する。
- ユーザーはフェーズの名称・狙いを編集できる。編集されたフェーズは `edited_by_user = true` となり、以降 AI による上書きの対象外となる。

## 6.4 UI デザイン方針

### 方向性

画面そのものをゲーム盤面として構成する方向を採用する。
検討時には次の三案を比較した。

| 案 | 内容 | 判断 |
|---|---|---|
| A | 実用寄り。落ち着いた配色の情報ツール | 不採用。ゲーム要素を中核とする D-2 と釣り合わない |
| B | 常時の画面は静かに保ち、達成の瞬間に演出を集中 | 不採用 |
| C | 画面全体をゲーム盤面として構成 | **採用**。開いた時点で動機が働くことを優先 |

視覚表現は近未来的なホログラム調の UI ジャンルに範を取る。
既存作品の UI を複製するものではなく、同ジャンルの表現手法を用いて独自に構成する。

### 構成要素

| 要素 | 内容 |
|---|---|
| 配色 | 背景 `#05090D` / 主色 シアン `#35E8FF` / 達成 `#6EE7A8` / 未達・警告 `#FF7A6B` / 休息 `#B98CFF` |
| 面 | 角を落としたパネル（`clip-path`）、罫線 `#143848`、進行中は `#1E5566` と外周の発光 |
| 書体 | 欧文 Rajdhani、和文 M PLUS 1。欧文ラベルは広い字間で見出しの上に配置 |
| 背景 | 52px 間隔の微細なグリッド |
| 記号 | ひし形のマーカー、細い罫、括弧状の角飾り |

### 配色の役割

色は状態を表すために用い、目標そのものの識別には用いない。
目標の識別は章番号とラベルで行う。目標数が増えた際に色が不足しないようにするためである。

| 色 | 意味 |
|---|---|
| シアン | 進行中、操作可能 |
| 緑 | 達成済み |
| 赤 | 未達、警告 |
| 紫 | 休息トークン |

### 画面固有の方針

- **フェーズ**は CHAPTER I〜IV の進行トラックとして表現する。現在地のノードのみ発光させる
- **未達（振り返り）画面**は罫と背景グリッドを赤系に切り替え、他の画面と明確に区別する
- **モバイル**では発光量を絞る。小さい画面では発光が可読性を損なうため。タップ対象は 44px 以上を確保する

## 7. 実装計画

| Phase | 内容 | 目安 |
|---|---|---|
| **Phase 1** | 記録機能、複数目標（アクティブ枠 3）、手動クエスト、認証と RLS。AI 連携なし | 1.5〜2 週 |
| **Phase 2** | XP / レベル / ストリーク / 休息トークン / 未達イベント生成 | 4〜5 日 |
| **Phase 3** | Vercel Cron + 無料枠 API によるクエストおよびフェーズの自動生成 | 4〜5 日 |
| **Phase 4** | Cowork MCP 連携（未達相談、insight 書き戻し、週次作戦会議） | 1〜2 日 |

合計見積: 3.5〜4.5 週（週末を主たる開発時間とする前提）

### 7.1 Phase 1 に AI を含めない理由

本プロジェクトにおける最大のリスクは「MCP 接続が機能するか」ではなく「利用者が記録を継続するか」である。
記録が継続しない場合、いかなる AI 機能を実装しても価値を生まない。
したがって、最もリスクの高い仮説から検証するという原則に従い、Phase 1 は AI を含まない最小構成とする。

なお、ゲーム要素は AI なしでも成立する（手動で作成したクエストの完了でも XP は付与される）。

## 8. 既知のリスクと留意事項

| リスク | 内容 | 対応 |
|---|---|---|
| 無料枠の縮小 | 無料枠 LLM API の上限は予告なく変更される（過去に大幅な削減実績あり） | プロバイダ抽象化により差し替え可能性を担保する |
| 外部 AI へのデータ送信 | 無料枠の入出力はモデル改善に利用される場合がある | 送信データを要約に限定。`goals.share_with_external_ai` により目標単位で除外可能 |
| Supabase の一時停止 | 無料プロジェクトは 7 日間の無操作で一時停止する | 日次利用を前提とする。停止時は手動で再開 |
| Cron の実行時刻 | Vercel Hobby では指定時刻の 1 時間以内に発火し、頻度は 1 日 1 回 | 日次生成には十分。高頻度化が必要な場合は pg_cron 等へ移行 |
| MCP のネットワーク経路 | カスタムコネクタの通信は Anthropic のクラウド側から発出する | Supabase は公開エンドポイントのため問題なし。ローカル資源への接続は不可 |
| 通知手段 | LINE Notify は 2025 年 3 月に終了済み | Discord Webhook または LINE Messaging API を検討 |
