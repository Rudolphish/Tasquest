# Tasquest 実装プラン

> 本書は `docs/design.md` の決定事項を実装に落とすための進め方を定める。
> 各手順について、成果物・検証方法・担当を明示する。

- 最終更新: 2026-09-12
- 前提: 設計確定済み（D-1〜D-11）

---

## 1. 順序の考え方

| # | 原則 | 理由 |
|---|---|---|
| 1 | スキーマを最初に確定させる | スキーマはフロントエンド・RPC・AI の三者が共有する唯一の契約であるため |
| 2 | RLS とスロット制約はテーブルと同じマイグレーションに含める | 後から追加する場合、既存データとの整合性確認が必要になり、かつ適用漏れが静かに通過するため |
| 3 | UI は機能の次に当てる。ただしダッシュボードのみ先行する | 機能変更のたびに装飾が手戻りするため後回しが原則だが、継続動機の検証には見た目が必要なため |
| 4 | AI 連携は最後に置く | Phase 1 の検証対象は「記録が継続するか」であり、AI はその後の拡張であるため |

## 2. 担当の区分

| 担当 | 内容 |
|---|---|
| 本人のみ可能 | Supabase プロジェクト作成と各キーの取得、Vercel へのプロジェクト接続、Gemini API キーの取得 |
| 実装側 | マイグレーション、型生成、アプリケーション実装、検証 |

本人の作業は 2 回に集約する。S1 適用前に 1 回（Supabase と Vercel）、S7 着手前に 1 回（Gemini）。

## 3. 検証環境について

Docker デーモンが利用できないため Supabase CLI のローカルスタックは起動できない。
代替として PGlite（WebAssembly 版 PostgreSQL）を用い、マイグレーションを実際に適用して検証する。
Supabase 固有の `auth.uid()` はスタブ関数で代替する。

## 4. 手順

### S1. スキーマ・RLS・制約（1 本のマイグレーション）

**成果物**
- `supabase/migrations/0001_init.sql` — 全テーブルを完成形で作成する（Phase 1 で使用しない `goal_phases` と `retrospectives` を含む）
- 全テーブルに対する RLS の有効化と所有者ポリシー
- `active_slot` に対する一意制約（アクティブ枠 3 件の保証）
- `total_xp` を `xp_events` の集計から導出するビュー
- RPC 3 本のシグネチャ（本体は S7 / S8 で実装し、この時点では定義のみ）

**検証**
PGlite にマイグレーションを適用したうえで、次を確認する。

- アクティブ枠 4 件目の INSERT が**拒否されること**
- 他ユーザーの行が RLS により**見えないこと**
- `xp_events` を経由しない `total_xp` の直接更新が**できないこと**

制約は「記述したこと」ではなく「違反を拒否したこと」をもって検証とする。

**所要**: 1〜2 日

---

### S2. 型生成とデータアクセス層

**成果物**
- マイグレーションから生成した TypeScript 型定義
- 型定義の生成器と、スキーマとの乖離を検出する検査
- クエリ関数を集約したモジュール（UI から直接クエリを組み立てない）

**当初案からの変更**

`supabase gen types` は CLI へのログインかデータベースパスワードを要求する。
認証情報の受け渡しを増やさないため、PGlite へマイグレーションを適用し、
その内省結果から型を生成する方式に変更した。副次的に、スキーマと型定義の
乖離を検査で検出できるようになっている。

**所要**: 0.5 日

---

### S3. 認証と画面の骨組み

**成果物**
- Supabase Auth による単一ユーザーのログイン
- ダッシュボードの空状態までの疎通

**注意（S-3 の項を参照）**: Server Component は API ルートの権限判定を経由しない。
RLS を唯一の防衛線とせず、ID を受け取るページでは関数内でも所有者を確認して `notFound()` を返す。

**所要**: 1 日

---

### S4. 記録フローの一周

**成果物**
- 目標の作成（アクティブ枠 3 件の制限を含む）
- クエストの手動作成
- クエストの完了
- 記録の入力と表示
- **ダッシュボードのみ** `docs/design.md` 6.4 節の視覚語彙を適用する

**検証チェックポイント**

ここで一度実装を止め、実際に 1 週間運用する。
本プロジェクト最大のリスクは「利用者が記録を継続するか」であり、これが確認できない限り後続の投資は回収できない。

**所要**: 4〜5 日 + 検証期間 1 週間

---

### S5. ゲーム層

**成果物**
- XP 付与（工数区分からの決定論的な算出）
- レベル、連続記録、休息トークン
- 未達判定の日次バッチと `retrospectives` の自動生成

**注意**: 連続記録の更新と未達イベントの生成は単一トランザクションで行う。
外部呼び出しや状態遷移は、成功を確認してから状態を進める（S-2 の項を参照）。

**所要**: 4〜5 日

---

### S6. デザインの全面適用

**成果物**
- 残り 5 画面への視覚語彙の適用
- 共通部品の抽出（角落としパネル、メーター、ひし形マーカー、章トラック）

**所要**: 3〜4 日

---

### S7. AI による自動生成（Phase 3）

**成果物**
- プロバイダ抽象層（差し替え可能性の担保）
- Gemini 実装
- Vercel Cron による日次実行

**注意（S-4 の項を参照）**: 「生成を試みた」と「生成できた」を区別する。
`ai_runs` に実行結果の状態を持たせ、失敗した実行が「本日は生成済み」と判定されないようにする。
生成に失敗した日を「クエスト 0 枚」で確定させない。

**所要**: 4〜5 日

---

### S8. Cowork 連携（Phase 4）

**成果物**
- Supabase リモート MCP の接続
- RPC 3 本の本体実装
- 未達相談から `insight` 書き戻しまでの疎通

**進め方**: `read_only` で読み取りのみ先に疎通させ、動作を確認してから書き込みを開放する。

**所要**: 1〜2 日

## 5. 過去の失敗から得た横断的な注意

同種構成（Next.js App Router / Supabase / Vercel）で記録された失敗のうち、本プロジェクトに該当するもの。

| # | 記録された事象 | 本プロジェクトでの該当箇所 | 対策 |
|---|---|---|---|
| S-1 | ページのデータ取得をキャッシュで包んでいたため、テーブルが存在しないのにページが正常表示された | マイグレーション適用の確認 | 移行の成否を画面表示で判断しない。クエリを直接実行して確認する |
| S-2 | 外部への送信が成功したか確認せずに状態を進めたため、通知が永久に失われ得る状態だった | 日次バッチ、通知 | 成功を確認してから状態を進める。失敗時は状態を進めない |
| S-3 | Server Component のページが API の権限判定を通らず、URL を知るだけで他人のデータが閲覧できた | `/goals/[id]` などの ID を受け取るページ | ページ関数内でも所有者を確認する。RLS を唯一の防衛線にしない |
| S-4 | 「取得を試みた」と「取得できた」を区別せず、失敗した取得が永久に再取得されなくなった | 日次クエスト生成、`ai_runs` | 判定は成功した実行の時刻に基づいて行う |
| S-5 | `loading.tsx` を置いたルートでストリーミングが開始され、`notFound()` の応答が 200 になった | 権限まわりの確認 | 権限の確認はステータスコードではなく応答本文で行う |

## 7. 補足：S3 で得られた知見

### `loading.tsx` を安易に置かない

`loading.tsx` を置いたルートは Next.js がストリーミングを開始し、本文より先に
応答ヘッダーを送る。その後に `notFound()` を呼んでも状態コードは変更できず、
200 のまま本文の途中で not-found 画面へ差し替わる（S-5）。

権限の確認を状態コードで行っていると、UI 都合のファイルを 1 つ追加しただけで
「権限が壊れた」ようにしか見えない失敗が起きる。現時点で `loading.tsx` は
置いていない。追加する場合は、権限の確認を応答本文で行う形へ先に変えること。

### Next.js 16 では `middleware` が `proxy` になった

ファイル名を `src/proxy.ts` とし、`proxy` という名前で関数を公開する。
`middleware` のままでも動作するが、非推奨の警告が出る。

### 転送先に外部から与えられた値をそのまま渡さない

認証後の転送先を問い合わせ文字列から受け取ると、任意の URL へ飛ばせる
踏み台になる。既知の経路と突き合わせ、一致しなければ既定の経路へ落とす。
`typedRoutes` を有効にしていると、この誤りが型検査で表面化する。
