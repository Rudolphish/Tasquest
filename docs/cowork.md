# Cowork からクエストを生成する

> Claude Cowork を Supabase に接続し、記録を踏まえてクエストを提案させる手順。
> 追加の課金は発生しない。Gemini API キーも不要である。

---

## 1. できること

```
Cowork に「今日のクエストを置いて」と頼む
  → Supabase MCP で目標・章・直近の記録を読む
  → propose_quests RPC でクエストを書き戻す
  → /today を開くとクエストが並んでいる
```

設計の D-5 における「週次は Cowork」に相当する。日次の自動生成（S7）を
入れる前に、まずこの形で運用し、毎回頼むことが負担になるかどうかを見極める。

---

## 2. 接続

### 2.1 プロジェクト参照を調べる

Supabase ダッシュボード → Settings → General → **Reference ID**。
`https://<reference-id>.supabase.co` の `<reference-id>` に一致する。

### 2.2 コネクタを追加する

Claude の設定 → Customize → Connectors → **Add custom connector**

| 項目 | 値 |
|---|---|
| 名前 | `Tasquest DB` など |
| URL | `https://mcp.supabase.com/mcp?project_ref=<reference-id>&features=database` |

初回の接続時にブラウザが開き、Supabase の認可を求められる。
個人アクセストークンを自分で発行する必要はない。

`project_ref` を付けて対象を 1 プロジェクトに絞る。付けない場合、
アカウント内の全プロジェクトが対象になる。

`features=database` を付けて、有効になる道具をデータベース操作のみに絞る。
省略すると、プロジェクトの作成や停止を含む広い範囲が有効になる。

### 2.3 書き込みについて

`read_only=true` を付けると読み取り専用になり、クエストを書き戻せない。
したがって本用途では付けない。

このとき Cowork は任意の SQL を実行できる状態になる。
下記の「守られること / 守られないこと」を理解した上で使う。

---

## 3. 守られること、守られないこと

MCP の接続はプロジェクトの管理権限で行われる。行レベルセキュリティを
経由しないため、「AI は RPC 経由でしか書けない」という方針（D-10）は、
この経路では規約であって強制ではない。

一方、データベースの制約として表現したものは、経路によらず守られる。

| 事項 | 経路によらず守られるか |
|---|---|
| XP 値は工数区分から決まる（生成列） | **守られる** |
| アクティブ枠は 3 件まで（一意索引） | **守られる** |
| XP は減算できない（検査制約） | **守られる** |
| 章は 4 つまで（検査制約） | **守られる** |
| 1 日のクエストは 3 枚まで | `propose_quests` を経由した場合のみ |
| 現在地は 2000 文字まで | **守られる**（検査制約） |

したがって、依頼文では `propose_quests` を使うよう明示する。
生成されたクエストが 1 日 4 枚以上になっていないかは、`/today` を見れば分かる。

なお 1 日 3 枚の上限を RPC のみに置いているのは意図的である。この上限は
AI による押し付けを防ぐためのものであり、利用者が自分の判断で 4 枚目を
手で置くことは妨げない。画面からの手動作成には上限を設けていない。

---

## 4. 現在地（background）を一緒にまとめる

AI が読めるのは Tasquest を使い始めてからの情報に限られる。使う前の経緯、
今の習熟度、時間や道具の制約は記録から読み取れない。目標ごとの
`background` にこれを書いておくと、提案の当たりが良くなる。

自分で書いてもよいが、壁打ちしながらまとめてもらうほうが早い。

```
Tasquest の「<目標名>」について、background（現在地）を一緒にまとめたいです。

まず私に質問してください。一度に全部ではなく、3〜4 問ずつにしてください。
聞いてほしい観点:
- 今どこにいるか（習熟度、手持ちの成果物、直近の状況）
- これまでの経緯（過去の試み、中断した理由）
- 制約（使える時間帯、頻度、道具、お金）
- やり方の癖（続いたやり方、続かなかったやり方）

私の答えが曖昧なときは、決めつけずに掘り下げてください。

一通り聞き終えたら、2000 文字以内の文章にまとめて見せてください。
- 事実と、私が言っていない推測を混ぜない
- 時間が経つと古くなる情報には、いつ時点かを添える
- 他の目標にも当てはまりそうな内容があれば、その旨を指摘してください
  （共通の制約は目標ごとに書くと重複するため、把握しておきたい）

私が確認して了承したら、public.record_background で保存してください。
了承する前に保存しないでください。
```

保存されると、目標の画面に「いつ・誰が書いたか」が表示される。人が書いた
ものを AI が上書きすることも、その逆もできる。禁じる代わりに履歴を残して
判断できるようにしてある。

現在地は時間とともに古くなる。区切りがついたときに、同じ手順でまとめ直す。

## 5. 依頼文

Cowork に貼る。

```
Tasquest の Supabase を見て、今日のクエストを提案してください。

手順:
1. goals から status = 'active' かつ share_with_external_ai = true の目標を読む
   background 列（現在地）を必ず読むこと
2. 各目標の goal_phases（あれば）と、logs の直近 7 日ぶんを読む
3. quests から直近の完了・未達の傾向を読む
4. 今日ぶんのクエストを最大 3 枚、全目標を横断して配分する
5. public.propose_quests を呼んで書き戻す

propose_quests に渡す形式:
[
  { "goal_id": "...", "title": "...", "why": "...", "effort": "S" | "M" | "L" }
]

守ってほしいこと:
- xp_value は渡さない。工数区分からシステムが決める
- title は、その日のうちに終わる具体的な行動にする
- why は「なぜ今日これなのか」を 1 文で書く。記録から読み取れた事実を根拠にする
- 直近で未達が続いている目標は、工数を 1 段階下げる
- background に書かれた制約（使える時間帯など）に反するクエストは出さない
- background が未記入の目標があれば、その旨を伝える。推測で埋めない
- INSERT を直接書かず、propose_quests を使う
```

書き戻したあと、`/today` を開いて確認する。

## 6. うまくいかないとき

| 症状 | 原因 |
|---|---|
| `目標が見つかりません` | 目標が進行中でないか、別のアカウントのもの |
| `進行中でない目標にはクエストを置けません` | 控えの目標を指している。先に配備する |
| `この目標は外部 AI との連携が無効です` | その目標の `share_with_external_ai` が false |
| `1 日あたり 3 枚までです` | 既にクエストがある。既存を消すか、翌日ぶんにする |
| `過去の日付にはクエストを置けません` | `due_on` が今日より前。履歴は後から作れない |
| `effort は S / M / L のいずれかです` | 工数区分の綴りが違う |

いずれの失敗でも、1 件でも不正があれば**何も登録されない**。
中途半端に一部だけ入ることはない。

---

## 7. これで足りるかを見極める

数日から 1 週間、この形で運用する。そのうえで判断する。

- 毎朝頼むのが苦にならない → S7（日次の自動生成）は不要かもしれない
- 頼むこと自体を忘れる、面倒 → S7 を実装する価値がある

S7 を入れる場合も、`propose_quests` はそのまま使える。`source` に
`gemini` を指定すれば、生成元が区別して記録される。
